# The Stars Barbershop — Firestore data model (draft)

Current production safety: `firestore.rules` DENIES ALL client access until authenticated workflows and security rules have been tested. **Do not enter real customer records into the current demo.**

## Collections (created automatically on first authorized write)

- `users/{firebaseAuthUid}`: `role` (owner | barber), `barberId` (barber only), `active`, `mustChangePassword`, timestamps. No plaintext password and no email in public screens.
- `barbers/{barberId}`: `firstName`, `lastName`, `username`, `alias` (optional), `phone` (optional), `active`, `authUid`, `createdAt`, `updatedAt`. **No photos, social images or password fields.**
- `appointments/{autoId}`: `barberId`, `firstName`, `lastName`, `phone` (optional), `date` (YYYY-MM-DD), `time` (HH:mm), `durationMinutes`, `serviceId`, `createdAt`, `updatedAt`.
- `walkins/{autoId}`: `barberId`, `firstName`, `lastName`, `date`, `time`, `createdAt`. No phone or service.
- `services/{serviceId}`: `name`, `durationMinutes`, `price` (optional), `active`, `sortOrder`.
- `schedules/{barberId}`: `weeklyHours`, `exceptions`, `updatedAt`.
- `settings/business`: public shop settings only; do not store credentials.

## Security and implementation requirements

1. Create owner account through an authorized administration procedure, never as a hardcoded web login.
2. Firebase Authentication must own passwords. Owner-triggered reset uses privileged server-side authority, short-lived temporary password and compulsory password rotation. Never expose Firebase Admin SDK secrets to browser or public GitHub.
3. Signed-in barber may access only their own data; owner may manage shop data; unauthenticated clients may create only validated bookings using a server-side workflow which atomically verifies availability, prevents overlapping appointments and rate-limits abuse.
4. Do not grant public reads on `appointments`, `walkins`, `users`, or private barber details.
5. Document any indexes generated by Firestore; use secure timestamps and ensure timezone handling in America/New_York.
6. For testing, create fake data only. Before launching: authorize snapshot/export, delete ALL demo bookings, walk-ins, barber accounts/profiles and test history while preserving ONLY the owner's authenticated account and owner user document. Verify counts and login.
7. Backups and restoration, access logging, data retention and incident response must be tested before production.
8. Firebase web configuration identifies a project; it is NOT an administrative credential. API key restrictions and App Check add abuse controls, but neither replaces authorization.

## Deployment strategy

The GitHub Pages demo currently uses localStorage and demo login. Keep that flow isolated until Firestore rules, backend booking validation and Firebase Authentication are complete. No live customer data should be written from demo code.
